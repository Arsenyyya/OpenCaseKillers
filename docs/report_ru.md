# ИИ-агент для анализа обращений

## Архитектура и запуск

Агент собирает обращения поддержки, выделяет повторяющиеся потребности и готовит карточки для продуктовых команд. В каждой карточке — частота, динамика и цитаты из источников. Решение о передаче в backlog принимает владелец продукта.

Приём данных, распознавание, анализ и доставка работают как отдельные сервисы. Права, версии и согласование контролируются кодом; модели обрабатывают содержание внутри корпоративного контура.

---

## 1. Как работает сквозной сценарий

### От запроса к продуктовому решению

1. **Получение.** Ingest читает новые и изменённые записи источника, принимает внешнюю версию и создаёт внутреннюю ревизию. Курсор, данные и задание обработки сохраняются одной транзакцией.
2. **Нормализация.** Media извлекает текст и формирует сегменты с происхождением: тикет, страница PDF или временной интервал аудио. Перед анализом очевидные персональные данные и секреты маскируются.
3. **Извлечение.** Analysis получает строго типизированный список отдельных потребностей. Каждая потребность сопровождается точной цитатой и `segment_id` той же ревизии. Validated extraction сохраняется до assignment: ожидание lease не тратит модельный бюджет повторно.
4. **Группировка.** Код находит ограниченный набор похожих групп одного продукта и класса. Модель выбирает существующую группу, новую группу или неопределённый случай. Частота пересчитывается из актуальных участий.
5. **Подборка.** Delivery формирует шаблонные карточки. По умолчанию нужны два независимых origin за 30 дней; в течение бизнес-дня выбираются до пяти разных новых или изменившихся карточек.
6. **Решение и доставка.** Reviewer принимает конкретную ревизию карточки. В режиме `reviewed` вместе с решением создаётся outbox-запись; отправитель повторно проверяет актуальность и полномочия.

### Пример: CSV

«Добавьте выгрузку заказов в CSV» — `feature_request`. «Работавшая выгрузка CSV сломалась» — `defect`. Эти потребности остаются в разных группах даже при общей теме экспорта. Смешанный тикет может дать оба элемента.

**Origin — независимое исходное обращение.** Обновления, вложения и повторная обработка не увеличивают частоту. Явные связи `duplicate_of` объединяют origin. Два независимых одинаковых текста считаются дважды. Количество обращений не называется количеством клиентов.

В демо Atlas имеет 12 независимых origin в группе пожеланий CSV. После изменения одной потребности и удаления другой частота становится 10. Дефекты экспорта учитываются отдельно.

## 2. Архитектура и процессы

Четыре границы сервисов реализованы одной кодовой базой. Общая инфраструктура — PostgreSQL; он хранит предметные данные, очередь заданий, leases, capacity slots и outbox.

| Сервис | Ответственность | Запуск |
|---|---|---|
| ingest | Change feed, курсоры, принятие ревизий, enqueue | `support-agent ingest` |
| media | Текст, документы, ASR/VL, сегменты и cache | `support-agent worker media` |
| analysis | Извлечение, retrieval, assignment и проверка evidence | `support-agent worker analysis` |
| delivery | API, дайджесты, решения и доставка | API, scheduler и sender отдельно |

В Compose дополнительно выделен `media-text`: резервный worker только для текстовых заданий. Большие вложения не занимают этот процесс. Generic media-worker также может обрабатывать текст. Получение заданий идёт по одному, без большого prefetch.

| Процесс Compose | Назначение |
|---|---|
| db / migrate | PostgreSQL и одноразовое применение Alembic-миграций |
| ingest / media / media-text / analysis | Фоновые этапы pipeline |
| delivery | FastAPI на локальном порту 8000 |
| scheduler | Периодическое построение подборок, вне API-worker |
| sender / retention | Доставка outbox и исполнение явно запрошенного удаления |

Планировщик не запускается в каждом API-worker. Redis, Kafka, отдельная векторная БД и агентный фреймворк в MVP не используются. Поведение задаёт ограниченный workflow: LLM интерпретирует содержание, а код управляет доступом, состоянием и записью.

Основные точки расширения: адаптер источника, модельный провайдер, хранилище вложений и получатель backlog. Корпоративный формат изолирован контрактом шлюза и не выдаётся за известный API компании.

## 4. Контент, модель и проверяемые источники

### Нормализация вложений

Текст и комментарии приходят как текст источника. Для DOCX и текстового слоя PDF применяется обычное извлечение. В смешанном PDF решение принимается по страницам: пригодный текст сохраняется, страницы без пригодного слоя передаются VL-провайдеру. Изображения PNG/JPEG идут в VL, PCM WAV — в ASR. Готовая пригодная расшифровка переиспользуется.

Фактический тип определяется по содержимому файла. Ограничиваются размер, число страниц, длительность и распаковка DOCX. Локальные декодеры работают в отдельных процессах: по умолчанию wall timeout 12 секунд и CPU limit 8 секунд; в Linux дополнительно 768 MiB адресного пространства. На macOS RLIMIT_AS не применяется.

Каждый сегмент хранит текст, `source_ref`, тип медиа, страницу либо время, версию обработчика и фактически сообщённое качество. Отсутствующий confidence остаётся неизвестным. Битое вложение, плохая расшифровка или неполное покрытие дают видимый `partial`/`needs_review`.

### Извлечение и поиск повторов

Классы: `feature_request`, `defect`, `service_request`, `incident`, `unclear`. Срочность — отдельное поле; при отсутствии оснований используется `unknown`. Модель не назначает product_id, ticket_id, права и владельца.

Pydantic запрещает лишние поля и проверяет типы. Цитата обязана быть точной подстрокой указанного канонического маскированного сегмента. Для невалидного JSON разрешена одна попытка исправления. Неуверенные items сохраняют review_reason и доступны через review-фильтр API. Длинный текст обрабатывается сегментами; общий бюджет вызовов сохраняется в БД.

Поиск использует PostgreSQL full-text/trigram и словарь синонимов: до 20 кандидатов, до 5 — в matching context. Matching получает ограниченное evidence, а не весь длинный тикет. Произвольный candidate_id отвергается. Неуверенный случай остаётся provisional и не попадает в автоматическую подборку.

**Предел интерпретации:** валидная цитата доказывает происхождение текста, а не правильность всей интерпретации. ASR-цитата подтверждает результат распознавания. Regex-маскирование очевидных данных не является полной DLP или гарантией анонимности.

## 5. Надёжность, изоляция и согласование

### Очередь и версии

Задания захватываются через `FOR UPDATE SKIP LOCKED`. Worker получает lease и уникальный claim token. После истечения lease другой процесс может забрать работу; старый token не может завершить новый claim. Heartbeat продлевает действующее владение. Во время модели или HTTP транзакция БД не удерживается.

Статусы: `queued`, `running`, `retry_wait`, `succeeded`, `dead`, `cancelled`. Временный сбой повторяется не более трёх раз с backoff/jitter и учётом Retry-After. Permanent error не повторяется как временная ошибка. Общие provider slots в PostgreSQL ограничивают число вызовов между процессами; после bootstrap по умолчанию доступны два слота на LLM, ASR и VL.

Внешняя версия может быть opaque ETag. Порядок задаётся sequence источника; внутренняя accepted revision монотонна. Поздний результат сверяет текущую ревизию и tombstone. Assignment сериализуется lease только внутри продукта; разные продукты продолжают работать параллельно.

### Кто имеет доступ

| Роль | Полномочия |
|---|---|
| viewer | Читать разрешённые группы, карточки и маскированные evidence |
| product_reviewer | Принимать решение по точной revision и content hash своего продукта |
| operator | Смотреть состояние, повторять допустимые dead jobs и запускать retention; без автоматического права reviewer |

В local/demo используются случайные bearer tokens, в БД — их хеши. Роли и продукты берутся из серверного реестра. В internal JWT проверяются по подписи RS256, issuer, audience и времени. FORCE RLS действует как дополнительный слой; runtime-роли не владельцы таблиц и не имеют BYPASSRLS. Scope выставляется локально на транзакцию.

Approval связано с полным snapshot карточки, включая период. В `shadow` внешних записей нет. В `reviewed` решение и outbox сохраняются атомарно. Перед отправкой проверяются актуальность карточки и права reviewer. Ключ доставки включает продукт, карточку и ревизию.

При неопределённом исходе используются idempotency key или строгий correlation lookup. Если получатель не поддерживает оба механизма, результат — `delivery_unknown` без слепого повторного создания. Уже отправленная устаревшая карточка требует контролируемой коррекции.

## 6. Запуск: Python на хосте и PostgreSQL в Docker

Этот вариант удобен для разработки, запуска тестов и чтения кода. Нужны Python 3.12+ и работающий Docker с Compose. Команды выполняются из корня репозитория.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install uv==0.13.7
.venv/bin/uv sync --frozen --extra dev --cache-dir .cache/uv
python3 scripts/bootstrap.py
docker compose up -d --wait db
.venv/bin/support-agent migrate
DELIVERY_MODE=reviewed .venv/bin/support-agent run-demo
```

`bootstrap.py` создаёт локальные случайные пароли и токены только при отсутствии файлов. `.env` и `.local/tokens.json` имеют режим 0600. Они остаются локальными и не входят в публичный Git.

### Ожидаемый результат на чистой БД

40 тикетов, 37 участий origin в группах, 6 карточек, 2 локальные доставки и `repeat_unchanged: true`. Участия — это пары origin/группа, а не число клиентов или полностью обработанных тикетов.

```sh
# Отдельный чистый сценарий, включая рестарт и удаление:
.venv/bin/python scripts/verify_demo.py

# API под ограниченной ролью agent_api:
.venv/bin/python scripts/start_api.py

# В другом терминале:
.venv/bin/python scripts/api_probe.py
```

OpenAPI: `http://127.0.0.1:8000/docs`. PostgreSQL: `127.0.0.1:55432`. Если порт 8000 уже занят запущенным Compose API, используйте существующий API или запустите host API с `--port 8001` и probe с `--url http://127.0.0.1:8001`.

Демонстрация использует фиксированные часы для воспроизводимости. Постоянные процессы работают по текущему времени UTC; рабочие дни рассчитываются в зоне Europe/Moscow.

## 7. Запуск всех процессов в Docker Compose

Один образ используется ingest, media, analysis и delivery-процессами. Скрипт сборки работает через временный ASCII-путь и обходит ошибку некоторых Docker Desktop при кириллице в пути проекта.

```sh
python3 scripts/bootstrap.py
sh scripts/build-image.sh
docker compose up -d --wait db
docker compose run --rm --no-deps -T migrate support-agent migrate
docker compose run --rm --no-deps -T bootstrap support-agent seed-demo
docker compose run --rm --no-deps -T \
  -e DELIVERY_MODE=reviewed bootstrap support-agent run-demo
docker compose up -d --no-build --wait --wait-timeout 60
docker compose ps
```

API: `http://127.0.0.1:8000/docs`. Наружу публикуются только локальные порты API и PostgreSQL. Данные БД находятся в `pgdata`, контейнерные credentials и local storage — в `agent-storage`. Обычный restart не требует повторной загрузки fixtures. Admin URL получают только migrate/bootstrap; API и workers его не наследуют.

### Проверка доступа без копирования токенов

```sh
docker compose exec -T ingest python scripts/api_probe.py \
  --url http://delivery:8000 --tokens /app/.local/tokens.json
```

Host- и container-файлы токенов — разные источники конфигурации. Local `seed-demo` обновляет серверный реестр по файлу своего окружения. Поэтому после Docker seed следует использовать контейнерный probe; после host seed — host probe. Не создавайте дополнительные копии токенов ради передачи проекта.

Доставка в `.env` по умолчанию `shadow`. Однократный `reviewed` demo отправляет карточки только локальному получателю. Для интерактивной доставки после решения включите `DELIVERY_MODE=reviewed` одновременно у API и sender и перезапустите их. Сам переход в режим не заменяет авторизованное решение.

```sh
# Повторный запуск окружения:
docker compose up -d --no-build --wait --wait-timeout 60
# Остановка без удаления данных:
docker compose stop
```

## 8. CLI и API для повседневной работы

| Действие | Команда |
|---|---|
| Получить новые изменения один раз | `support-agent ingest-once` |
| Запустить этап | `support-agent worker media` / `media_text` / `analysis` / `delivery` |
| Подготовить подборку продукта | `support-agent build-digest atlas` |
| Посмотреть метрики | `support-agent metrics` |
| Проверить удаление по сроку | `support-agent retention atlas` |
| Явно выполнить удаление | `support-agent retention atlas --execute` |

В host-варианте перед командой используется путь `.venv/bin/`. Scheduler запускается отдельно: `support-agent scheduler`. Флаг `worker <kind> --once` выполняет ограниченный drain только выбранного stage; для полного пути используйте run-demo или verify_demo.py.

| HTTP API | Назначение |
|---|---|
| `/health/live`, `/health/ready` | Жизнеспособность и готовность обязательных зависимостей |
| `GET /products/{p}/groups`, `/cards` | Разрешённые группы и карточки с пагинацией |
| `GET /products/{p}/evidence/{revision_id}` | Маскированные сегменты и покрытие обработки |
| `GET /products/{p}/digest?period=YYYY-MM-DD` | Сохранённая подборка по продукту и периоду |
| `POST /products/{p}/cards/{id}/decision` | Решение reviewer по revision/hash |
| `GET /products/{p}/pipeline` | Состояние и ошибки заданий для operator |
| `POST /products/{p}/jobs/{id}/retry` | Разрешённый повтор dead job |
| `POST /products/{p}/retention` | Dry-run либо постановка retention job |
| `GET /metrics` | Закрытые метрики для operator |

Пример тела решения; hash берётся из полученной карточки:

```json
{
  "revision": 1,
  "content_hash": "<hash из карточки>",
  "decision": "accepted",
  "reason": "Потребность подтверждена владельцем продукта"
}
```

Также доступны `rejected` и `needs_clarification`. Поддельные роли, чужой product_id и stale revision блокируются кодом и ограничениями БД. Swagger UI описывает HTTP-запросы; публичного debug-endpoint с содержимым БД нет.

## 9. Что проверено и что означают результаты

Автоматическая проверка: 86 тестов прошли за 133,54 секунды, lint/формат/schema drift также прошли. Команда проверки — make check. Тестовые сценарии проверяют исторический purge, hard TTL, повторную синхронизацию, review, reconciliation, installed wheel и полный HTTPS/JWT путь. Тесты используют временные БД и независимые процессы для concurrency.

| Проверка | Результат и смысл |
|---|---|
| Сквозной путь | 40 синтетических тикетов → 6 карточек → 2 локальные доставки |
| Replay и restart | Количество карточек и доставок не увеличивается |
| Update/delete | CSV origin Atlas 12 → 10; удалённые raw/evidence очищаются |
| Дубли | Независимые одинаковые тексты считаются отдельно; duplicate graph пересчитывается, циклы отвергаются |
| Изоляция | Чужие объекты, подделанные роли и quotes блокируются; scope не остаётся в connection pool |
| Конкуренция | Два процесса не получают один действующий lease; старый token не коммитит новый claim |
| Model failures | JSON/schema/evidence validation, один repair, ограниченный retry и общий budget |
| Доставка | Обрыв после записи не даёт дубль при сверке; без возможностей сверки — unknown |
| Длинные тикеты | Последний сегмент не теряется; matching context ограничен evidence |

### Нагрузочная проверка очереди

В нагрузочном прогоне обработаны **3000 из 3000** заданий четырьмя процессами за **36,295 секунды**. Пик одновременно занятых model slots — **2 при лимите 2**. Имитировались временные ошибки и суточный backlog; разные продукты конкурировали за общую capacity.

Это измерение PostgreSQL-очереди и координации при mock latency. Оно не измеряет Qwen/GPU, полный аудио/изображений профиль или production throughput. Ориентир 95% записей за 24 часа остаётся целью пилота.

```sh
.venv/bin/pytest -q
.venv/bin/ruff check src tests scripts migrations
.venv/bin/support-agent load-test --tickets 3000 --workers 4
.venv/bin/support-agent evaluate
```

Без независимого gold-набора и реальных internal results команда `evaluate` возвращает `not_run`. Управляемые demo-ответы не используются для объявления precision/recall реальной модели.

## 10. Эксплуатация и настройки

| Параметр по умолчанию | Значение |
|---|---|
| Опрос источника / размер страницы | 600 секунд / 20 изменений |
| Lease / попытки | 90 секунд / максимум 3 |
| Provider timeout / slots | 20 секунд / по 2 слота на LLM, ASR, VL |
| Файлы / размер / PDF | 8 на тикет / 10 000 000 bytes / 30 страниц |
| Аудио / сегменты | До 1200 секунд WAV / до 80 сегментов |
| Контекст / потребности / вызовы | 16 000 символов / до 12 items / до 12 model calls на ревизию |
| Кандидаты / matching | До 20 найденных / до 5 переданных |
| Порог / окно / retention | 2 origin / 30 дней / 90 дней для каждой ревизии |

Значения задаются через `Settings` и переменные окружения. Capacity slots инициализируются bootstrap; число уже существующих слотов не меняется горячим переключением `MODEL_SLOTS`. Изменять capacity нужно в остановленном контуре с проверкой активных leases.

### Реакция на сбои

Оператор начинает с pipeline API и метрик. В логах — безопасные идентификаторы и error_code; исходный prompt, токены и provider body не печатаются. Dead retry не сбрасывает сохранённый model budget и не возрождает удалённую ревизию.

`delivery_unknown` требует сверки по correlation key и записи результата через outbox resolve API/CLI. Подтверждение not_delivered останавливает отправку до нового accepted от reviewer. `correction_required` означает, что получатель мог сохранить старую карточку: нужна контролируемая коррекция или отзыв. Автоматический корпоративный edit/revoke API не заявлен.

Удаление и отзыв доступа создают tombstone, отменяют задания, убирают content/evidence/cache и участия, инвалидируют snapshots и outbox. Поздний worker не должен восстановить удалённые данные. Hard TTL каждой ревизии не продлевается обновлением тикета. Старые копии очищаются по provenance даже после смены группы; свежая текущая ревизия сохраняется. Retention имеет dry-run и batches 100–500.

Для аварийной остановки доставки остановите sender и scheduler, проверьте неопределённые исходы и переведите сервисы в shadow. Не удаляйте volumes для обычного restart. Корпоративный backup/restore и согласование внешних записей требуют отдельного runbook.

## 11. Как подключить внутренний контур

Внутренний режим включается явно: `MODE=internal`, `APP_ENV=internal`. Он не переключается на demo при ошибке реального endpoint. Неполная обязательная конфигурация блокирует старт. Начните с provision --config ... --dry-run и doctor; реальные sub и права задаёт администратор.

| Что предоставить | Для чего |
|---|---|
| `GATEWAY_URL`, `GATEWAY_TOKEN`, `ALLOWED_HOSTS` | Доверенный HTTPS-шлюз; запрет произвольных URL и redirect |
| `INTERNAL_CA`, если нужен | Проверка TLS внутренним CA без verify=False |
| `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_PUBLIC_KEY` | Проверяемый issuer и RSA public key не менее 2048 bits |
| Реестр продуктов, owners и grants | Серверное назначение scope и reviewer |
| Ordered change feed, версии и удаления | Надёжные cursor/sequence, immutable ticket snapshots и tombstones |
| Возможности backlog | Idempotency key либо строгий lookup; процедура коррекции |
| Сборки и мощность моделей | Реальные лимиты контекста, качества, concurrency и времени |

Контракт шлюза спроектирован для этого проекта. Это **не подтверждённый API компании**. Группы endpoints: `/v1/products/{product}/...`, `/v1/models/extract`, `/v1/models/match`, `/v1/models/media`, `/v1/backlog/...`. Форматы запросов задаются строгими JSON Schema.

Используются внутренние Qwen 3.8, Qwen-ASR и Qwen-VL. Веса не скачиваются автоматически, внешние LLM/API в runtime не подставляются. Demo-провайдер ограничен fixtures и не понимает произвольные новые тексты как универсальная модель.

### Граница готовности

До пилота нужны реальные endpoints/issuer, capacity и независимая разметка; согласованная retention/DLP политика, backup/restore и security-review. Admin secrets уже отделены от runtime. Provision загружает owners, verified sub/bindings, cursors, slots и trusted known-task catalog без demo. Реальный медиа/GPU профиль и 24-часовой SLO не проверены.

В репозитории есть работающий локальный путь, воспроизводимые проверки и документированные адаптеры. Эти результаты позволяют начать техническую интеграцию и пилот, сохраняя явное разделение проверенного поведения и внешних допущений.
